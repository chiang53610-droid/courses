# 評估入門

這一課（以及後面的另外八課）著重在**撰寫 LLM 使用情境評估**的方法，這是開發 AI 應用程式的關鍵環節。

在快速發展的人工智慧領域中，大型語言模型已經成為各行各業的強大工具。然而，要充分發揮這些模型的潛力，光是「把它做出來」是不夠的——還需要仔細的**評估**和**優化**。這就是「提示詞評估」（簡稱「**evals**」）登場的地方。

下面是我們內部「解決方案架構師」團隊說明評估為什麼這麼重要的兩段真實引言：

>The (in)ability for teams to measure the performance of their models is the biggest blocker of production use cases for LLMs and also makes prompting an art instead of a science
>（團隊能不能衡量模型的表現，是 LLM 正式上線最大的障礙；做不到的話，寫提示詞就只是一門藝術，而不是科學。）

>even though evals take a lot of time, doing them up front will save developer time in the long run and result in better products getting out much sooner
>（雖然評估要花很多時間，但一開始就做，長期來看會節省開發者的時間，讓更好的產品更快推出。）

開發者沒有寫評估，主要有兩個原因：
1. 很多人對「評估」這整個概念不熟悉
2. 不清楚實際上要怎麼實作評估

這門課的目標，就是解釋這兩件事：**評估是什麼**，以及**怎麼寫評估**。

這堂入門課處理第一件事：介紹評估的概念，並概述撰寫評估的各種方法。

## 基準測試（Benchmarks）

在深入「客戶評估」之前，我們先花點時間討論一種大多數人都熟悉的評估形式：**模型基準測試**。

模型基準測試就像 AI 世界的**標準化考試**。就像 SAT（美國大學入學考試）成績應該能讓大學大致了解一個學生的學業能力，模型基準測試讓我們大致了解一個 AI 模型在各種任務上的表現。

開發大型語言模型的公司會執行這些基準測試，來展示他們的模型能做什麼。你可能看過一些名字很奇怪的測驗，例如 ARC、MMLU 或 TruthfulQA，上面有亮眼的分數。這些基準測試涵蓋從基本的閱讀理解，到各領域的進階推理和知識。它們很適合用來比較不同的模型，以及追蹤 AI 能力的整體進展。你可能看過顯示基準測試分數的「模型卡」：

![模型基準測試分數表](../../prompt_evaluations/images/benchmarks.png)

雖然這些基準測試很適合拿來炫耀，也能大致呈現模型的能力，但它們並不是故事的全部。這有點像知道一個人的 IQ 分數——它也許（也許不！）能告訴你這個人的一般智力，但它**沒辦法告訴你這個人適不適合做你這份特定的工作**。

## 客戶評估（Customer evaluations）

想像你剛買了一把閃亮的新瑞士刀。它有幾十種工具和小配件，但你主要是想在露營時用它來**開罐頭**。當然，它還能修指甲、開紅酒很棒，但它開罐頭到底好不好用？這就是大型語言模型需要「提示詞評估」的原因。

LLM 就像處理文字的**超強瑞士刀**。它們能用語言做各種了不起的事，從寫詩到寫軟體都行。但當你把 LLM 用在一個特定的任務上——例如回覆客服信件或產生商品描述——你需要知道它在**那份特定工作**上表現得怎麼樣。

這就是提示詞評估（簡稱 evals）出場的時候。**提示詞評估**（也叫做客戶評估）是一種有系統的測試，用來衡量 LLM 在**你的特定使用情境**上表現得有多好。它們是連接「LLM 的通用能力」和「你商業應用的獨特需求」之間的關鍵橋樑。透過實作穩健的評估，你可以確保模型和提示詞的組合，不只符合一般的基準，還能在你需要它完成的特定任務上表現出色。

評估的主要好處包括：

* **反覆改善提示詞**——在我的特定任務上，第 2 版的提示詞有沒有比第 1 版好？
* **部署前後、修改提示詞前後的品質保證**——我們最新的提示詞修改，有沒有造成「退步（regression）」？
* **客觀地比較模型**——我們能不能換成 Anthropic 最新的模型，並維持或提升目前的評估表現？
* **可能的成本節省**——我們能不能換成 Anthropic 最便宜、最快的模型，並維持目前的評估表現？

> 🧩 **白話小補充：「退步（regression）」是什麼？** 你改了提示詞，修好了 A 問題，卻不小心讓原本正常的 B 情況壞掉了。有評估的話，每次修改後重跑一次，就能馬上發現這種「按下葫蘆浮起瓢」的情況。

在撰寫和優化提示詞時，我們遵循一個**以評估為核心**的反覆流程：

![以評估為核心的提示詞開發流程圖](../../prompt_evaluations/images/process.png)

* 我們先**開發測試案例**，等一下會詳細介紹。
* 接著，為特定的使用情境**寫一份提示詞的草稿**。
* 然後，用我們的測試案例**測試提示詞**，衡量模型在這個任務上做得有多好。我們想要得到某種「**基準分數（baseline score）**」。
* 有了基準分數之後，就可以**修改提示詞並重複這個流程**。

評估的重點，就是用**數字指標**來量化「提示詞 + 模型」組合的品質。**沒有量化的衡量，我們怎麼知道提示詞的修改是不是真的有改善？**

## 一個評估包含哪些東西？

一個設計良好的提示詞評估，由四個主要部分組成：

* **範例輸入（Example Input）**：給模型的指示或問題。設計能準確代表你的應用程式在真實世界中會遇到的輸入，是非常關鍵的。
* **標準答案（Golden Answer）**：正確或理想的回答，作為模型輸出的比較基準。要做出高品質的標準答案，通常需要**領域專家**的參與，以確保準確和相關。
* **模型輸出（Model Output）**：LLM 根據輸入提示詞實際產生的回答。這就是你要拿來和標準答案比較評估的東西。
* **分數（Score）**：代表模型在這個輸入上表現的量化或質化數值。評分方法會依照任務的性質和你選擇的評分方式而不同。

![評估的四個組成部分示意圖](../../prompt_evaluations/images/eval_diagram.png)

> 🧩 **白話小補充**：就像考試——**範例輸入**是考題、**標準答案**是老師的解答、**模型輸出**是學生的答案卷、**分數**是批改後的成績。

**我們一般建議至少準備 100 組「測試案例 / 標準答案」才能得到最好的結果。不過為了讓跟著這門課學習的人節省 API 費用，我們大部分的評估都會用少很多的組數。**

### 範例評估資料集

想像我們要用 LLM 來**分類顧客的客訴**。一個（非常小的）評估資料集可能長這樣：

```py
eval_data = [
    {
        "complaint": "The app crashes every time I try to upload a photo",
        "golden_answer": ["Software Bug"]
    },
    {
        "complaint": "My printer isn't recognized by my computer",
        "golden_answer": ["Hardware Malfunction"]
    },
    {
        "complaint": "I can't figure out how to change my password",
        "golden_answer": ["User Error"]
    }
]
```

（三筆資料：「每次我想上傳照片 App 就當掉」→ 軟體錯誤；「我的電腦認不出我的印表機」→ 硬體故障；「我不知道怎麼改密碼」→ 使用者操作錯誤。）

每一則輸入的客訴，都附上一個對應的標準答案分類。我們會在後面的課程延伸這個例子，學習怎麼執行並批改這個評估。

> 🧩 **白話小補充**：這就是 [0-4 第 7 節](../00_before_you_start/04_python_crash_course.md#7-把串列和字典組合起來claude-的訊息格式) 學過的「串列裡裝字典」。`golden_answer` 用串列，是因為有些題目可能有不只一個正確答案。

## 評分方法

選擇正確的評分方法，對評估的成效非常關鍵。每種方法都有它的優點，適合不同類型的任務。

### 人工評分（Human-based grading）

對於需要細膩理解或主觀判斷的任務，人工評分仍然是**黃金標準**。這個方法是請人——通常是領域專家——審閱模型的輸出、評估品質，並給每個輸出打分數。

人工評分擅長評估語氣、創意、複雜的推理，或專家級領域中的事實正確性。在處理開放式任務、或答案是否正確取決於細微的情境因素時，它特別有價值。缺點是**耗時**而且可能**很貴**，特別是大規模的評估。它也容易因為**不同評分者之間的標準不一**而不一致。

人工評分的形式包括：

* **專家審查**：由領域專家評估回答的準確度和深度。例如一個討論房貸方案的銀行聊天機器人，可能需要律師人工審閱它的回答，確保符合公平借貸的法律，並正確地呈現條款。皮膚科醫師可能會評估模型提供的皮膚癌篩檢建議，檢查辨識是否正確、緊急程度是否適當，以及是否符合最新的研究。
* **使用者體驗評審團**：由一群人評估輸出的清晰度、有用程度、吸引力，以及其他需要人類判斷的面向。

### 程式評分（Code-based grading）

程式評分使用程式化的方法來評估模型的輸出。這個方法非常適合**有明確、客觀標準**的任務。例如，如果你用 LLM 從文字中擷取特定的資料，你可以用程式碼檢查擷取出來的資訊是否符合預期的值。

程式評分的主要優點是**速度快、可大規模擴展**。一旦設定好，它可以快速且一致地處理成千上萬筆評估。但它處理細膩或主觀回答的能力有限。常見的程式評分技巧包括：完全字串比對、檢查關鍵字是否出現，以及用正規表達式做模式比對。

程式評分的形式包括：
* **完全字串比對評分**——這是最嚴格的形式，模型的輸出必須和標準答案**一字不差**。就像只有一個正確答案的選擇題。例如地理小測驗的問題「法國的首都是哪裡？」唯一被接受的答案就是「Paris」。
* **關鍵字出現**——這個方法檢查模型的輸出是否包含某些關鍵的字詞，不管它們的順序或上下文。例如在一個產品客服聊天機器人中，「我要怎麼重設我的 SmartHome 溫控器？」這個問題，可能要求回答中必須包含「hold（按住）」、「button（按鈕）」、「5 seconds（5 秒）」和「blinking light（閃爍的燈）」這些關鍵字。
* **正規表達式（Regex）**：我們可以定義正規表達式來檢查複雜的文字模式。例如一個評估信用卡申請資格的銀行聊天機器人，可能要求回答符合 `"Your credit score of \d{3} (qualifies|does not qualify) you for our \w+ Card"` 這個模式（意思是「您 3 位數的信用分數（符合／不符合）我們某某卡的申請資格」），確保它同時提供了分數和結果。
* 還有很多其他的方法！

> 🧩 **白話小補充：看懂那個正規表達式**
> - `\d{3}`：剛好 3 個數字（例如 720）
> - `(qualifies|does not qualify)`：「qualifies」或「does not qualify」其中之一（`|` 代表「或」）
> - `\w+`：一個以上的英文字母或數字（例如卡片名稱 Platinum）

### LLM 評分（LLM-based grading）

LLM 評分介於程式評分和人工評分之間。這個方法用**另一個 LLM**（有時候是同一個）來評估輸出。只要精心設計評分用的提示詞，就能利用 LLM 的語言理解能力，評估各式各樣的標準。

這個方法比程式評分能處理更複雜、更主觀的評估，又比人工評分更快、更能大規模進行。但是，它需要純熟的提示詞工程才能確保結果可靠，而且評分的 LLM 總是有可能帶入它自己的偏見。

模型評分的形式包括：
* **摘要品質**——這份摘要有多簡潔、多準確？
* **語氣評估**——這個回答是否符合我們的品牌準則或說話語氣？
* **任何其他品質！**——我們可以自訂評分準則（rubric），讓大型語言模型用任何我們想得到的指標來評分輸出：這個輸出有多誠懇地道歉？輸出有沒有提到競爭對手？

## 結論

實作穩健的提示詞評估，是開發有效 LLM 應用程式的關鍵步驟。透過有系統地測試和修改提示詞，你可以確保你的應用程式提供一致、高品質、符合你特定需求的結果。記住，投入在建立好評估上的時間，會以更好的表現、更容易的優化，以及對 LLM 解決方案更大的信心作為回報。

## 📌 重點整理

- **基準測試**（MMLU 等）像標準化考試，只能看出模型的「一般能力」；**客戶評估**才能告訴你模型在「你的任務」上表現如何。
- 評估的好處：比較提示詞版本、防止退步、比較模型、找出更便宜的模型。
- 一個評估 = **範例輸入 + 標準答案 + 模型輸出 + 分數**；建議至少 100 組測試案例。
- 三種評分方法：

| 方法 | 優點 | 缺點 | 適合 |
|---|---|---|---|
| 人工評分 | 最能判斷細膩品質（黃金標準） | 慢、貴、標準不一 | 語氣、創意、專業領域 |
| 程式評分 | 快、便宜、一致、可大規模 | 無法處理主觀的回答 | 完全比對、關鍵字、正規表達式 |
| LLM 評分 | 能評估主觀標準，又能自動化 | 評分提示詞要寫好；可能有偏見 | 摘要品質、語氣、自訂準則 |
